## What the working tree actually was

The session opened on 310 uncommitted files. Most of it was a repo-wide Oxfmt
reformat, but underneath sat an **unfinished native DNS security hardening
pass** with three failing gates. Finishing it was the whole job.

The hardening itself (already authored, kept): Android DNS-over-HTTPS removed
(`HttpURLConnection` 4 -> 0), native bridge pinned to port 53 on both
platforms, every native query pinned to the allowlisted zone, native allowlist
narrowed to the two LLM zones.

## The allowlist invariant: containment, not equality

`nativeSecurityPolicy.test.ts` asserted the native allowlist was **set-equal**
to the TypeScript `ALLOWED_DNS_SERVERS` (6 hosts). The hardening narrowed
native to 2. Three constraints could not all hold at once:

| Constraint | State | Demanded |
|---|---|---|
| `androidDnsResolver.policy.spec.ts` | new | native = 2 LLM zones, no public resolver |
| `dnsService.spec.ts`, `settings.migration.spec.ts` | untouched | `validateDNSServer("8.8.8.8")` succeeds |
| `nativeSecurityPolicy.test.ts` | untouched | native set-equal to TS's 6 |

Resolution: the invariant is **containment**. Native may be stricter; it must
never list a host TS would reject. Both platforms must narrow identically, or
one user setting succeeds on iOS and fails on Android — that cross-platform
assertion is now in the test too.

**Mistake worth remembering:** I first restored native to 6, reasoning the
IP-resolver path was a real documented feature (`composeDNSQueryName` maps an
IP resolver to the default zone, and `DNS-PROTOCOL-SPEC.md` documents it). Then
I found the *new* Android spec explicitly forbidding public resolvers — the
narrowing was deliberate, and the author's own zone-pin comment had misled me
into thinking otherwise. Reverted. Lesson: when a spec file is *modified* in
the tree, diff it against HEAD before inferring intent from source comments.

## Behavioral consequence to remember

Selecting an IP resolver now fails the native rung and falls through to
UDP/TCP. With **Allow Experimental Transports** off, the order is native-only,
so an IP resolver has no rung left and the query fails outright. Verified by
reading the transport loop (`continue` on method error) and `methodOrder`
construction — not assumed. Documented in SYSTEM-ARCHITECTURE and
DNS-PROTOCOL-SPEC.

## Autoreview findings

**Fixed — dnsjava relative name (real leak).** dnsjava treats a name with no
trailing dot as relative and walks the system search path, so the legacy
Android fallback put `<query>.<local-search-domain>` on the wire, handing the
user's internal search domain to the DNS server. `isExpectedLegacyTxtRecord`
already rejected those *answers*, so no out-of-zone data was ever accepted —
the leak was in the query, not the response. Now
`Name.fromString(queryName, Name.root)`. Guarded twice: a spec assertion, and
the JVM stub deliberately omits the `Lookup(String, int)` overload so a
regression **fails to compile**.

**Deferred — iOS cancellation ordering race (real, unfixed).** `queryTXT` and
`cancelActiveQueries` create independent unstructured Tasks funnelling to the
same MainActor state, with no ordering guarantee; a cancel can be admitted
before an earlier query and report zero cancellations. A correct fix needs a
lock-protected cancellation generation read outside the MainActor, spanning
`DNSResolver` and `RNDNSModule`. **This repo has no iOS test target**, so the
ordering cannot be verified here — shipping unverified native concurrency was
judged worse than the bounded race, whose impact is capped by the JS
`assertLifecycleActive` guard rejecting stale results. Recorded in CHANGELOG.

## Two CI bugs that only surfaced now

CI on `main` was **already red** before this session, failing at
`verify:typed-routes` — so `pnpm run test` had not run in CI for some time.
Fixing that exposed a second, hidden failure.

1. **typed-routes**: `@expo/router-server` debounces `regenerateDeclarations`,
   so `setupTypedRoutes` resolves before `router.d.ts` is written. Passed
   locally against a stale file, failed on a clean checkout. Now deletes the
   file first and polls, so a pass proves regeneration.
2. **`repo.lint.spec.ts`**: asserted `output.not.toContain("error")` on a clean
   Oxlint run. The linux-x64 binding prints `Found 0 warnings and 0 errors.` —
   a *success* message containing "errors" — while darwin-arm64 prints nothing.
   Identical oxlint 1.79.0, green locally, red in CI. Now asserts the reported
   error count is zero and that no violation-fixture rule id appears.

## decode-uri-component: suppressed, not fixable

CVE-2026-45822 / GHSA-vcc3-ghjq-m6fr, CWE-400 algorithmic-complexity DoS, CVSS
6.6 moderate, reached through `query-string` -> `expo-router`. The only patched
release, `0.5.0`, is **ESM-only** (`"type": "module"`, no `require` condition
in `exports`) while `query-string` `require()`s it from the Metro CJS bundle.
Every 0.2/0.3/0.4 release is inside the vulnerable range, so there is no
version to move to; forcing 0.5.0 would break the app bundle at runtime.

Used the repo's existing `auditConfig.ignoreGhsas` with a blocker and recheck
date (2026-10-01) rather than raising `--audit-level high`, which would have
silenced every future moderate. `pnpm audit` now reports
`1 moderate (1 ignored)` and still fails on anything new.

## Not verified

Build 85 has **no physical-device install proof**. The authorized iPhone stayed
locked for the whole session, so the developer disk image could not mount
(`CoreDeviceError 12040`) and `devicectl` could neither install nor launch.
`xcodebuild` named the cause directly in its destination list: the device
needs to be unlocked to enable development services. The archive compiles and
TestFlight validates, but nobody has run it on hardware — and this release
changes DNS transport behavior, which is exactly what a device would exercise.
Recorded in README and CHANGELOG rather than letting `VALID` imply more than it
does.
